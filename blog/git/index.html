GIT MASTERCLASS

THE SOFTWARE ENGINEER'S DEFINITIVE GUIDE TO GIT

Git is not just a tool to upload code to GitHub with git add . && git commit -m "update" && git push. It is a distributed, content-addressable directed acyclic graph (DAG) of snapshots. When you understand how commits, branches, and the HEAD pointer work under the hood, you gain complete superpower over your codebase: clean branch histories, fearless rebasing, effortless conflict resolution, and the ability to time-travel and rescue lost work from any disaster.

1. THE GIT MENTAL MODEL: THE 4 TREES & COMMITS

Most developers struggle with Git because they try to memorize commands without understanding where their code actually lives. Git manages code across four distinct zones:

ZoneWhere It LivesWhat It RepresentsKey Commands
1. Working DirectoryLocal Disk filesYour active uncommitted files that you edit in your IDE.git status, git diff
2. Staging Area (Index).git/indexThe staging staging dock; exact snapshot queued for the next commit.git add, git restore --staged
3. Local Repository.git/objectsPermanent commits recorded into your local branch history (HEAD).git commit, git reset, git log
4. Remote RepositoryGitHub / GitLabThe shared remote source of truth for the entire team.git push, git fetch, git pull
💡 What is a Commit really? A commit is NOT a diff/patch! It is a complete snapshot of your repository files at that exact instant, stored as a 40-character SHA-1 (or SHA-256) hash. Each commit points to its parent commit(s), author name, email, timestamp, and commit message.

What is the HEAD Pointer?

HEAD is simply a pointer to the branch or commit you are currently looking at on your local machine. Normally, HEAD points to a branch name (e.g. HEAD -> main).

⚠️ What is a "Detached HEAD"? If you run git checkout <commit-hash>, HEAD now points directly to a commit instead of a branch. If you make commits in this state, they will be orphaned when you switch away!
How to fix it: Simply create a new branch from this point: git switch -c my-rescued-work.

2. DAILY ESSENTIALS: THE CLEAN DEVELOPER WORKFLOW

The standard loop every software engineer uses multiple times per day:

bash 
# 1. One-time Setup: Identity & modern defaults
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

# Automatically set upstream branch on first push (No more typing --set-upstream!):
git config --global push.autoSetupRemote true

# 2. Start a new repo or clone an existing one
git init
git clone https://github.com/user/repo.git

# 3. Check current state (Use short format for clean readability!)
git status -s

# 4. Interactive Staging: Review line-by-line before committing (Super Pro Tip!)
git add -p file.js   # Interactively choose chunks (hunks) of code to stage

# 5. Commit with atomic, descriptive messages
git commit -m "feat(auth): implement JWT token refresh handler"

# 6. Fetch updates without touching your working files
git fetch origin

# 7. Pull changes with rebase instead of messy merge commits
git pull --rebase origin main

# 8. Push to remote
git push

3. BRANCHING & REMOTE SYNCHRONIZATION

Branches are ultra-lightweight in Git — literally just a 41-byte text file containing the SHA hash of the latest commit. Creating a branch costs virtually zero memory and milliseconds of time.

💡 Modern Tip: Stop using git checkout for branches. Since Git 2.23, Git split the confusing overloaded checkout command into git switch (for branches) and git restore (for files).
bash 
# 1. List all local and remote branches
git branch -a

# 2. Create and switch to a new feature branch
git switch -c feature/payment-gateway
# (Legacy alternative: git checkout -b feature/payment-gateway)

# 3. Switch back to main
git switch main

# 4. Rename a branch
git branch -m old-name new-name             # Rename currently active branch
git branch -m <old-name> <new-name>         # Rename another branch

# 5. Delete a branch safely (only if merged)
git branch -d feature/login

# 6. Force-delete an unmerged branch (careful!)
git branch -D feature/abandoned-experiment

# 7. Delete a branch on the REMOTE server (GitHub)
git push origin --delete feature/login

# 8. Prune stale remote tracking branches (Clean up deleted PR branches locally)
git remote prune origin  # or: git fetch -p

4. MERGE VS. REBASE: THE DEFINITIVE COMPARISON

This is the #1 question software engineers argue about. Both merge and rebase combine changes from one branch into another, but they do it in fundamentally different ways.

🔀 Git Merge (The Non-Destructive Stitch)

Integrates history by creating a new Merge Commit with two parents. It never touches or rewrites past commits.

  • Pros: 100% preserves original history, timestamps, and commit order. Perfect audit trail.
  • Cons: Creates cluttered "railroad track" graphs with dozens of noisy "Merge branch 'main' into feature" bubbles.

⚡ Git Rebase (The Linear History Rewriter)

Lifts your feature commits and replays them one-by-one onto the tip of target branch (main), creating brand new commit hashes.

  • Pros: Produces a completely straight, linear, immaculate git log. Easy to trace bugs with git bisect.
  • Cons: Rewrites commit hashes. Requires force pushing if already pushed to remote.

Visual History Comparison

Original: main: A --- B --- C feature: D --- E After 'git merge main': main: A --- B --- C --------- \ feature: D --- E ------- M (New merge commit M created) After 'git rebase main': main: A --- B --- C feature: D' --- E' (Commits replayed on top of C with new hashes!)
🚨 The Golden Rule of Rebasing:
NEVER rebase commits that exist on a public shared branch (like main or develop). Only rebase your local private feature branches before opening or merging a Pull Request!

5. INTERACTIVE REBASE: SQUASH, REWORD & CLEAN COMMITS

During a normal workday, you might create messy commits: "wip", "fix typo", "try again", "tests pass finally". Before submitting a PR to code review, professional engineers use Interactive Rebase to squash those into one beautiful, atomic commit.

bash 
# Interactively review and modify the last 4 commits:
git rebase -i HEAD~4

Git opens your text editor with a list of commands. You simply change the word in front of the commit:

pick e3a12f1 feat(ui): build login screen component squash 4b29f03 fix button alignment squash 8d1c720 update padding reword 9f3a11b add unit tests for login validation # Commands: # p, pick <commit> = use commit # r, reword <commit> = use commit, but edit the commit message # e, edit <commit> = use commit, but stop for amending # s, squash <commit> = meld into previous commit and combine commit messages # f, fixup <commit> = like "squash", but discard this commit's log message # d, drop <commit> = remove commit completely

Save and close the file. Git will prompt you for a single unified commit message. Now your 4 messy commits are fused into 2 clean, atomic commits!


6. STEP-BY-STEP MERGE & REBASE CONFLICT RESOLUTION

Merge conflicts occur when two branches modify the exact same lines of code in a file. Git refuses to guess which version is correct, giving you full control.

bash 
# Step 1: Start the rebase or merge
git rebase main
# Git pauses: "CONFLICT (content): Merge conflict in src/app.js"

# Step 2: Check which files are in conflict
git status
# Conflicted files show as: "both modified: src/app.js"

# Step 3: Open the conflicted file. You will see Git conflict markers:
<<<<<<< HEAD (Current branch code)
const API_URL = "https://api.v2.company.com";
=======
const API_URL = "https://api.gateway.company.com";
>>>>>>> incoming commit

# Step 4: Delete the markers (<<<<<<<, =======, >>>>>>>) and keep the desired code.

# Step 5: Stage the resolved file
git add src/app.js

# Step 6: Continue the rebase (DO NOT COMMIT!)
git rebase --continue

# If you ever get stuck or panicking, abort and return safely to before the rebase:
git rebase --abort   # (Or: git merge --abort)

7. UNDO, REWIND & DISASTER RECOVERY

Every developer makes mistakes. Git provides three levels of undo tools depending on what you want to rewind:

ScenarioCommandEffect
Unstage a file (keep local edits)git restore --staged file.jsRemoves file from staging area without touching your code.
Discard all uncommitted edits in a filegit restore file.jsReplaces file on disk with the clean version from HEAD.
Discard ALL uncommitted changes everywheregit restore . && git clean -fdReverts all tracked files and deletes untracked files/folders.
Amend the last commitgit commit --amend --no-editAppends newly staged files into the previous commit.
Undo commit, keep changes stagedgit reset --soft HEAD~1Moves branch pointer back 1 commit; all code remains staged.
Undo commit, keep changes unstagedgit reset --mixed HEAD~1Default reset. Code remains in working directory as unstaged edits.
Destroy last commit and changesgit reset --hard HEAD~1Obliterates commit and wipes working directory to previous commit.
Safely undo a published remote commitgit revert <commit-hash>Creates a brand new commit that reverses the changes. Safe for team repos!

8. THE ULTIMATE SAFETY NET: git reflog

Have you ever run git reset --hard by accident, or deleted a branch before pushing, and felt your heart drop into your stomach? Don't panic. In Git, almost nothing is truly lost for at least 30 to 90 days.

🛡️ The Reflog Guarantee: Git keeps a local chronological audit log (Reference Log) of every single time your HEAD pointer moved — every checkout, commit, reset, rebase, and merge.
bash 
# 1. View your local history tape
git reflog

# Outputs something like:
# 3b4a2e1 HEAD@{0}: reset: moving to HEAD~1
# a7f8902 HEAD@{1}: commit: implement payment webhook (YOUR LOST WORK!)
# 9c1234e HEAD@{2}: checkout: moving from main to feature/pay

# 2. Resurrect your lost commit by creating a branch pointing directly to it:
git switch -c recovered-work a7f8902

# Boom! All your "deleted" code is back safely.

9. STASHING & CHERRY-PICKING

Real-world engineering often interrupts your work with emergency hotfixes or context switches.

Git Stash: The Temporary Pocket

Allows you to cleanly stash away your dirty uncommitted changes, switch to another branch, and restore them later:

bash 
# Stash with a descriptive note (including untracked new files):
git stash push -u -m "wip: auth middleware refactor"

# Working directory is now completely clean! Switch and fix that production bug:
git switch hotfix/critical-bug
# ... fix bug, commit, and push ...

# Return to your feature branch and pop your stashed changes back:
git switch feature/auth
git stash pop

# Other helpful stash commands:
git stash list      # View all saved stashes
git stash apply     # Restore stash without removing it from the stash stack
git stash drop      # Discard a specific stash
git stash clear     # Delete all stashes

Git Cherry-Pick: Steal a Specific Commit

Grab a specific bugfix or feature commit from another branch without merging the entire branch:

bash 
# Apply commit 8f2c3b1 onto your currently checked-out branch:
git cherry-pick 8f2c3b1

# Cherry-pick without immediately committing (lets you inspect edits first):
git cherry-pick -n 8f2c3b1

10. CODE ARCHAEOLOGY: LOG, DIFF, BLAME & BISECT

Reading code history and finding when regressions were introduced is a superpower:

bash 
# 1. Gorgeous one-line commit tree with visual branch lines
git log --oneline --graph --decorate --all

# 2. View line-by-line diff between working tree and staged code
git diff            # What you haven't staged yet
git diff --staged   # What is staged for next commit

# 3. View diff between two branches
git diff main..feature/auth

# 4. Git Blame: Find who modified lines 20-35 of a file and in which commit
git blame -L 20,35 src/payment.js

# 5. Git Bisect: Binary search to find the EXACT commit that broke production
git bisect start
git bisect bad                 # Current commit is broken
git bisect good v1.2.0         # v1.2.0 was known to be working

# Git checks out intermediate commits. Test each one:
git bisect good   # (or: git bisect bad)
# After ~7 steps in a 1,000-commit history, Git identifies the exact culprit commit!

11. TAGGING & SOFTWARE RELEASES

Tags bookmark specific milestones (releases, semantic versions like v1.0.0) in your commit history:

bash 
# Create an annotated release tag (Recommended for releases)
git tag -a v1.0.0 -m "Release version 1.0.0: Production deployment"

# List tags matching pattern
git tag -l "v1.*"

# Push a specific tag to remote
git push origin v1.0.0

# Push all local tags to remote
git push origin --tags

# Delete a tag locally and remotely
git tag -d v1.0.0
git push origin --delete v1.0.0

12. SOFTWARE ENGINEER'S FREQUENTLY ASKED QUESTIONS (FAQ)

Practical solutions to the exact situations software engineers encounter on the job:

FAQ 01 How can I rebase my feature branch on top of the latest main?

First, fetch the latest commits from your remote repository, then rebase:

git fetch origin
git switch feature/my-feature
git rebase origin/main

If conflicts occur, resolve them, run git add <file>, and run git rebase --continue.

FAQ 02 How can I delete or undo a commit without losing my code?

Use a soft reset. This undoes the commit but leaves all your modified code staged in your index, ready to re-commit:

git reset --soft HEAD~1

If you want the changes to remain on your disk but unstaged, use git reset --mixed HEAD~1 (or simply git reset HEAD~1).

FAQ 03 Can I change a commit ID, and why did my commit hash change after rebasing?

You cannot manually edit a commit ID because in Git, the commit ID is a cryptographic hash computed from the tree contents, author, timestamp, commit message, and parent commit hash. If you change even a single character in the message or 1 byte of code, the hash mathematically changes to a completely new ID!

When you rebase, Git replays your changes with new parent pointers, so rebasing automatically generates brand new commit IDs.

FAQ 04 How can I rename a branch (both locally and on remote GitHub)?

Follow these 3 simple commands:

# 1. Rename locally (switch to it first):
git switch old-branch-name
git branch -m new-branch-name

# 2. Push new branch and set upstream tracking:
git push -u origin new-branch-name

# 3. Delete old branch from GitHub:
git push origin --delete old-branch-name
FAQ 05 How can I change the last commit message or add forgotten files?

Use --amend:

# To change just the commit message:
git commit --amend -m "feat: updated message"

# To add a forgotten file into the previous commit:
git add forgotten_file.js
git commit --amend --no-edit
FAQ 06 How do I discard all local uncommitted changes and return to a clean state?

To wipe all modifications to tracked files and delete any newly created untracked files:

# Revert all modified files back to HEAD:
git restore .

# Delete all untracked files and new directories:
git clean -fd
FAQ 07 I accidentally deleted a branch or ran git reset --hard! How do I recover it?

Use git reflog to find the commit hash before the mistake:

git reflog
# Find the hash, e.g. b4c1809 HEAD@{1}: commit: my feature
git switch -c recovered-branch b4c1809
FAQ 08 How do I unstage a file I accidentally added with git add?

Use git restore --staged (leaves your file edits intact on disk):

git restore --staged filename.js

# Or to unstage all files at once:
git restore --staged .
FAQ 09 How do I squash multiple messy commits into one single clean commit?

Run interactive rebase for the last N commits:

git rebase -i HEAD~3

In the text editor, keep the first commit as pick, and change the remaining commits to squash (or s) or fixup (or f to discard extra messages). Save and close!

FAQ 10 What is the difference between git pull and git fetch?

git fetch downloads the latest commits and branches from the remote server into your .git repository, but does not alter your local working files.

git pull is a two-step shorthand: it runs git fetch followed immediately by git merge FETCH_HEAD (or git rebase if configured), merging remote changes directly into your active branch.

FAQ 11 What is the difference between git reset and git revert?

git reset rewinds history by moving the branch pointer backward. It deletes or unstages commits. Use it for local, unpushed commits only.

git revert creates a new commit that inverses the changes of an older commit. It does not rewrite history, making it 100% safe to use on public/shared remote branches.

FAQ 12 How do I stop tracking a file (.env or secrets) without deleting it from disk?

Use git rm --cached:

git rm --cached .env
echo ".env" >> .gitignore
git commit -m "chore: stop tracking .env file"
FAQ 13 Why should I use git push --force-with-lease instead of --force?

git push --force blindly overwrites the remote branch. If your teammate pushed commits to that branch in the meantime, their code is instantly destroyed!

git push --force-with-lease checks whether anyone else has pushed new commits to the remote branch before overwriting. If new commits exist, it aborts safely and prevents data loss.

FAQ 14 How can I pull/checkout a single file from another branch?

Use git restore --source (or git checkout):

git restore --source=main src/config.json
# (Legacy equivalent: git checkout main -- src/config.json)
FAQ 15 How do I change the author name and email of my last commit?

Run:

git commit --amend --author="New Name <newemail@example.com>" --no-edit
