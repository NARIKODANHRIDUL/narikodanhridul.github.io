INTER-CORE COMMUNICATION: SCRATCHPAD (SPM) & COMMON PACKET MEMORY (CPM)

When a computer chip has two or more processor cores running together, they need a fast way to talk to each other without slowing down. Normal computer methods like operating system sockets or big shared caches are too slow and unpredictable for real-time systems like cars or robots. Instead, hardware designers use two smart memory areas: Scratchpad Memory (SPM) (a core's private, super-fast notepad) and Common Packet Memory (CPM) (a shared mailbox where messages are exchanged safely using simple Full Checks and Empty Checks).

1. ARCHITECTURAL FOUNDATIONS OF MULTI-CORE IPC

When two processor cores (like a phone's main CPU and its real-time sensor chip) need to share data fast, normal operating system pipes are far too slow. They waste time switching modes and jumping through operating system layers.

Instead, embedded chips use fast on-chip memory split into two simple parts:

  • SPM (Scratchpad Memory): A private, super-fast memory area connected directly to each core. It has zero waiting time.
  • CPM (Common Packet Memory): A shared mailbox memory where both cores can read and write messages in order (First In, First Out).

2. SPM VS. CPM: THE MEMORY HIERARCHY DICHOTOMY

Why not put everything in one shared memory pool? Because in real-time systems, bus contention destroys execution predictability.

💡 What is Scratchpad Memory (SPM)? Unlike hardware caches that automatically fetch cache-lines based on tag matching (introducing jitter and cache misses), an SPM is an explicit SRAM address space managed directly by the software programmer. Access is guaranteed to take 1 CPU cycle, giving absolute timing determinism.
💡 What is Common Packet Memory (CPM)? CPM (also called Common/Circular Packet Memory or Mailbox RAM) is dual-ported or multi-banked SRAM mapped to a common address space accessible by both Core A and Core B. Because concurrent accesses over the bus matrix can suffer arbitration wait-states, software only touches CPM to transfer finalized packets.

3. CIRCULAR RING BUFFER MECHANICS & POINTER MATHEMATICS

Inside the CPM, packets are organized as a bounded Circular Ring Buffer (FIFO). Two pointers coordinate the communication:

  • Head Pointer (Write Index): Owned and incremented strictly by the Sender. Points to the slot where the next packet will be deposited.
  • Tail Pointer (Read Index): Owned and incremented strictly by the Receiver. Points to the slot from which the next packet will be consumed.

4. THE SENDER'S PERSPECTIVE & RESPONSIBILITIES

The Sender is the **Producer**. It originates telemetry, sensor frames, or command packets in its private workspace and is held strictly accountable for never corrupting or overflowing the shared queue.

📤 Sender's Step-by-Step Lifecycle

  1. Step 1: Staging in Local SPM: Assemble, compute, and validate the packet checksum inside fast local SPM without touching the shared bus.
  2. Step 2: Perform FULL CHECK: Read the current Tail pointer from CPM. Verify that (Head + 1) % CAPACITY != Tail.
  3. Step 3: Handle Full Condition: If full, DO NOT WRITE. Either drop packet, block, or yield CPU to avoid overwriting unread data.
  4. Step 4: Copy Payload to CPM: Burst transfer the payload from local SPM into CPM_Buffer[Head].
  5. Step 5: Execute Memory Barrier (DMB): Force the CPU pipeline and write buffers to flush the payload before updating the pointer!
  6. Step 6: Advance Head Pointer: Commit Head = (Head + 1) % CAPACITY in CPM header.
  7. Step 7: Ring Doorbell (IPC Interrupt): Assert hardware mailbox interrupt or inter-core semaphore to alert Receiver Core.

🛑 Why the Full Check is Life or Death

If the sender fails to execute a strict Full Check:

  • Buffer Overflow: The write pointer overtakes the read pointer, trampling across packets the receiver has not yet read.
  • Corrupted Packets: The receiver reads a Frankenstein packet: half new data, half old data!
  • False Empty State: If Head laps Tail and lands exactly on Head == Tail, the system suddenly believes the buffer is completely empty, losing every single queued message!

5. THE RECEIVER'S PERSPECTIVE & RESPONSIBILITIES

The Receiver is the **Consumer**. It ingests packets from the CPM, executes business logic, and is responsible for releasing occupied buffer slots back to the sender.

📥 Receiver's Step-by-Step Lifecycle

  1. Step 1: Wakeup / Interrupt ISR: Receive IPC doorbell interrupt or poll periodic task scheduler.
  2. Step 2: Perform EMPTY CHECK: Read Head and Tail from CPM. Verify that Head != Tail.
  3. Step 3: Handle Empty Condition: If empty, exit immediately. Prevents reading stale or uninitialized memory slots.
  4. Step 4: Ingest Data into Local SPM: Burst copy packet payload from CPM_Buffer[Tail] into Receiver's local SPM for zero-latency processing.
  5. Step 5: Execute Memory Barrier: Ensure data read has fully committed before incrementing the tail pointer.
  6. Step 6: Advance Tail Pointer: Commit Tail = (Tail + 1) % CAPACITY. This instantly frees the slot for the sender!
  7. Step 7: Clear Interrupt / Send ACK: Clear pending interrupt flag or trigger space-available notification to Sender Core.

⚠️ Why the Empty Check is Life or Death

If the receiver fails to execute a strict Empty Check:

  • Buffer Underflow: The receiver reads stale, garbage, or deallocated memory contents.
  • Phantom Processing: Processing the same old command twice (e.g. executing duplicate transactions or duplicate motor impulses).
  • Synchronization Loss: Tail advances beyond Head, causing inversion of the queue state.

8. EMBEDDED C IMPLEMENTATION: DRIVER & BUFFER LOGIC

Here is a production-grade C implementation of an IPC ring buffer designed for bare-metal or RTOS multi-core controllers. Notice how we use volatile and memory barrier commands so the computer never skips writes or reads old cached data:

c 
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

#define CPM_QUEUE_CAPACITY 8      // Must be power of 2 for optimal modulo
#define PACKET_PAYLOAD_SIZE 64    // Fixed 64-byte payload

// Memory barrier macro (ARM architecture example)
#define MEMORY_BARRIER() __asm__ volatile("dmb ish" ::: "memory")

// Individual message packet structure
typedef struct {
    uint32_t message_id;
    uint32_t payload_len;
    uint8_t  payload[PACKET_PAYLOAD_SIZE];
    uint32_t checksum;
} IpcPacket_t;

// Shared Ring Buffer mapped directly into CPM memory address space
typedef struct {
    volatile uint32_t head;       // Owned by Sender
    volatile uint32_t tail;       // Owned by Receiver
    IpcPacket_t slots[CPM_QUEUE_CAPACITY];
} IpcRingBuffer_t;

// Pointer to hardware CPM shared RAM base address (e.g. 0x38000000)
volatile IpcRingBuffer_t * const g_cpm_channel = (IpcRingBuffer_t *)(0x38000000);

/* ==========================================================================
   SENDER CORE IMPLEMENTATION (Producer)
   ========================================================================== */
bool ipc_sender_send_packet(const IpcPacket_t *spm_packet) {
    uint32_t current_head = g_cpm_channel->head;
    uint32_t current_tail = g_cpm_channel->tail;
    
    // 1. FULL CHECK: Verify space is available
    uint32_t next_head = (current_head + 1) % CPM_QUEUE_CAPACITY;
    if (next_head == current_tail) {
        // Buffer is FULL! Cannot write.
        return false; // Error: Buffer overflow avoided
    }
    
    // 2. Copy payload from Local SPM into target CPM slot
    memcpy((void *)&g_cpm_channel->slots[current_head], spm_packet, sizeof(IpcPacket_t));
    
    // 3. MEMORY BARRIER: Ensure payload is fully committed before pointer update
    MEMORY_BARRIER();
    
    // 4. Advance Head pointer in shared CPM
    g_cpm_channel->head = next_head;
    MEMORY_BARRIER();
    
    // 5. Trigger hardware doorbell interrupt to notify Receiver Core
    // HW_TRIGGER_IPC_INTERRUPT(CORE_RECEIVER_ID);
    return true;
}

/* ==========================================================================
   RECEIVER CORE IMPLEMENTATION (Consumer)
   ========================================================================== */
bool ipc_receiver_get_packet(IpcPacket_t *spm_dest) {
    uint32_t current_head = g_cpm_channel->head;
    uint32_t current_tail = g_cpm_channel->tail;
    
    // 1. EMPTY CHECK: Verify new messages exist
    if (current_head == current_tail) {
        // Buffer is EMPTY! No pending messages.
        return false; // Underflow avoided: Do not read stale data
    }
    
    // 2. Copy payload from CPM into Receiver's fast local SPM
    memcpy(spm_dest, (const void *)&g_cpm_channel->slots[current_tail], sizeof(IpcPacket_t));
    
    // 3. MEMORY BARRIER: Ensure read completes before updating tail
    MEMORY_BARRIER();
    
    // 4. Advance Tail pointer to release slot back to Sender
    g_cpm_channel->tail = (current_tail + 1) % CPM_QUEUE_CAPACITY;
    MEMORY_BARRIER();
    
    return true;
}

9. EDGE CASES, MEMORY BARRIERS & HARDWARE HAZARDS

In high-speed multi-core silicon, subtle hardware mechanics can break seemingly perfect software logic:

⚠️ Hazard 1: Out-of-Order Execution & Missing Barriers
Modern CPUs re-order memory writes to optimize bus throughput. If the Sender executes head = next_head before the payload memory copy has finished draining to the CPM SRAM bus, the Receiver Core will wake up, see the updated head, and read unwritten or corrupt payload bytes!
Remedy: Always place a hardware Data Memory Barrier (DMB on ARM, sfence/mfence on x86) between the payload write and the pointer update.
⚠️ Problem 2: Cache Memory & Stale (Old) Reads
If the shared CPM memory is saved in a local core cache, the receiver core might read an old saved copy from its own cache instead of the fresh data in shared memory!
Remedy: Map the shared CPM region as Device Memory / Non-Cacheable (Strongly Ordered) via the MPU/MMU, or explicitly execute cache invalidation instructions (DC IVAC) prior to reading.
💡 Hazard 3: The "Reserved Slot" Rule
Notice why a queue of capacity $N$ can only store $N - 1$ items:
• If $N=8$, and we stored 8 items, head would equal tail!
• But head == tail is the exact definition of an EMPTY queue!
By dedicating 1 slot as a sentinel guard, head == tail strictly means Empty, and (head + 1) % N == tail strictly means Full, eliminating all ambiguity without requiring an extra counter variable.
